# قاعدة بيانات التدريب

تعديل الرسائل: PATCH /api/messages/:id يغيّر message فقط بشرط id وuser_id من الجلسة في استعلام واحد. النص مطلوب ومن1 إلى5000 حرف بعد إزالة الفراغات الطرفية. النجاح200 مع id وmessage وcreated_at؛ تاريخ الإرسال والاسم والمالك تبقى كما هي. الرسالة المفقودة أو التي لا تملكها ترجع404، والرقم أو النص غير الصالح400. لا يحتاج تعديلًا على المخطط.

حذف الرسائل: DELETE /api/messages/:id يستخدم شرط id وuser_id من الجلسة في استعلام حذف واحد. لا يحذف رسائل الحسابات الأخرى أو الرسائل القديمة بدون صاحب، ويرجع 404 لهاتين الحالتين وللرقم غير الموجود دون تمييز. الرقم غير الصالح يرجع 400 والنجاح 204. لا يحتاج تعديلًا على مخطط قاعدة البيانات.

نستخدم PostgreSQL محليًا. إعدادات الاتصال محفوظة في `.env` في جذر المشروع، وليس داخل `frontend`.
ملف `.env.example` يوضح أسماء المتغيرات فقط. كلمة المرور الفعلية تبقى في `.env` المتجاهل من Git.

## الملفات

- `src/config/db.js`: تحميل الإعدادات وإنشاء Pool مشترك لاتصالات PostgreSQL.
- `database/schema.sql`: تعريف جدولي `messages` و`users`.
- `scripts/setup-db.js`: إنشاء قاعدة `PGDATABASE` إذا لم تكن موجودة، ثم تنفيذ تعريف الجدول.
- `scripts/check-db.js`: فحص الاتصال باستعلام قراءة فقط.

## الأوامر

من جذر المشروع:

```bash
npm run db:setup
npm run db:check
```

الإعداد المحلي الافتراضي: `localhost:5432`، وقاعدة `fullstack_practice`، ومستخدم `postgres`.
إذا أردت استخدام pgAdmin، سجّل سيرفر بهذه البيانات وأدخل كلمة المرور من `.env` محليًا.
هذا المستخدم مخصص لإعداد بيئة التدريب المحلية؛ عند تجهيز نشر حقيقي نستخدم حساب تطبيق محدود الصلاحيات.

جدول `messages` يحتوي `id` و`name` و`message` و`created_at`.
طلب `POST /api/messages` يحفظ الرسالة عبر Service ثم Repository، ويرجع السجل المحفوظ مع `id` و`created_at`.

جدول `users` يحتوي `id` و`name` و`email` و`password_hash` و`created_at`.
الفهرس الفريد على `LOWER(email)` يمنع تكرار البريد حتى عند اختلاف حالة الأحرف.
طلب `POST /api/auth/register` يتحقق من البيانات والإيميل المكرر، ثم يعمل Hash لكلمة المرور باستخدام scrypt ويحفظ الحساب عبر `user.repository.js`.
الرد الناجح `201` يحتوي `id` و`name` و`email` و`created_at` فقط. البريد المكرر يرجع `409`، والبيانات غير الصالحة ترجع `400`.
طلب `POST /api/auth/login` يتحقق من بيانات الدخول بمقارنة كلمة المرور بالـHash، ويرجع `200` عند التطابق أو `401` عند عدم التطابق.
بعد نجاح الدخول، الرد يحتوي `data.user` و`data.expiresIn` فقط؛ التوكن يرسل في HttpOnly Cookie باسم access_token.
JWT موقّع بـHS256 وصلاحيته 900 ثانية. الـSecret محفوظ في `.env` على الباك فقط.
الـToken يحتوي `sub` لرقم المستخدم وبيانات الإصدار وانتهاء الصلاحية وissuer وaudience، بدون الإيميل أو كلمة المرور أو الـHash.
واجهة الدخول تحتفظ ببيانات المستخدم فقط في React Context، والمتصفح يحتفظ بالتوكن في HttpOnly Cookie لمدة 900 ثانية ويرسلها باستخدام credentials: include. SameSite=Strict وPath=/api وSecure في production. عند فتح الصفحة، تسترجع الواجهة الحساب عبر GET /api/auth/me مع Cookie. الرد يتضمن بيانات المستخدم والمدة المتبقية الفعلية دون تجديد التوكن، وبـCache-Control: no-store. الجلسة المفقودة أو المنتهية ترجع 401.
زر الخروج يستدعي POST /api/auth/logout لمسح Cookie قبل مسح حالة الواجهة. التوكن المسروق سابقًا يظل صالحًا حتى انتهاء مدته؛ لا توجد قائمة إبطال.
مسار إرسال الرسائل محمي بالتوكن الموجود في Cookie، ولا يقرأ Authorization Bearer. لا يوجد Refresh Token بعد.

إرسال الرسائل يتطلب الآن Cookie تحتوي JWT صالحًا وحسابًا موجودًا. user_id واسم المرسل يؤخذان من الحساب على السيرفر. شغّل npm run db:setup لإضافة عمود user_id وفهرسه؛ الرسائل القديمة تبقى بدون صاحب. الرسالة مطلوبة وبحد أقصى 5000 حرف.

GET /api/messages يستخدم user_id من الحساب المسجّل فقط ويرجع id وmessage وcreated_at بالأحدث أولًا ثم id تنازليًا عند تساوي الوقت. الرد Cache-Control: no-store، و200 مع مصفوفة فارغة إذا لم توجد رسائل، و401 بدون جلسة صالحة. الرسائل القديمة بدون user_id لا تظهر لأي حساب.
